Computer Use Agent

核心不是“让模型会点鼠标”，而是把 视觉输入、坐标执行、上下文管理、安全边界、失败诊断 做成一套可靠工程系统。

一句话结论

Browser / Computer Use Agent 的上限由模型决定，但下限由 harness 决定。大多数“不靠谱”不是推理失败，而是截图缩放、坐标映射、上下文爆炸、权限环境或安全策略没设计好。

文章最重要的 8 条 Best Practice

01 视觉

先缩放截图，再发给模型

如果截图超过 API 图像上限，服务端会静默 downscale，模型看到的坐标空间和你的执行坐标会错位。

02 坐标

display 尺寸必须等于实际图片尺寸

模型返回的是 display_width/display_height 坐标，执行前要缩放回真实屏幕坐标。

03 提示

文本指令放在截图前

content 数组中先放“要找什么/做什么”，再放图，能提高点击定位准确性。

04 模型

机械点击和复杂推理可拆模型

Sonnet 更适合稳定点击；Opus 适合强推理/高分辨率/复杂任务；可用 orchestrator + executor。

05 小目标

小控件不要硬点

checkbox、托盘图标、小箭头等应优先 zoom、键盘导航、DOM/JS 操作或放大 UI。

06 安全

网页内容一律视为不可信

prompt injection 是 computer use 的核心风险，提交表单、发消息、付款、改数据必须人审。

07 上下文

截图会快速吃满上下文

每张图约 1000–1800 tokens，长任务必须 rolling buffer + prompt cache + compaction。

08 可观测

失败要能回放

记录每步截图、模型 thinking、tool call、坐标 overlay，才能知道是模型没看懂还是 harness 错。

0→1 架构蓝图

一个可靠的 Computer / Browser Use Agent 可以拆成 5 层。不要一开始就写复杂 prompt，先把这 5 层跑通。

1

环境层

浏览器/桌面、登录态、网络、文件权限、视口、DPI。

2

感知层

截图、DOM、URL、accessibility tree、页面状态。

3

决策层

模型规划下一步，选择 click/type/scroll/DOM/JS。

4

执行层

坐标缩放、动作执行、等待页面稳定、异常恢复。

5

治理层

日志、回放、安全确认、上下文压缩、成本控制。

第一性原理：为什么很多 Browser Use 会失败

看错

截图过大被压缩、DPI=2、低分辨率丢细节、目标太小、弹窗不在截图里。

点错

display 尺寸不匹配、坐标没 scale back、窗口滚动后状态变化、点击后未等待稳定。

忘了

截图堆满上下文，历史被截断；compaction 没保留用户原始约束和失败尝试。

被攻击

网页、邮件、文档中可能包含“忽略用户指令”这类 prompt injection。

环境不对

云端浏览器没有用户登录态、本地文件、企业内网、插件或本机窗口状态。

不可观测

没有截图回放、坐标 overlay、tool result 日志，只能猜失败原因。

Harness 最小实现：别让坐标系统坑你

固定 720p 默认方案

适合 4.6 系列和大多数网页任务。关键是：你发给模型的图片尺寸、tool 声明的 display 尺寸、模型返回坐标所在空间，三者必须一致。

display_w, display_h = 1280, 720
resized = screenshot.resize((display_w, display_h))

tool = {
  "type": "computer_20251124",
  "name": "computer",
  "display_width_px": display_w,
  "display_height_px": display_h,
  "enable_zoom": True,
}

screen_x = int(api_x * screen_w / display_w)
screen_y = int(api_y * screen_h / display_h)

诊断口诀

  • 总是偏一边：多半是尺寸或 DPI 错。
  • 大概区域对、小目标 miss：用 zoom / keyboard / DOM。
  • 点了相似按钮：指令不够具体，要给位置和上下文。
  • 全局都差：截图超过上限或分辨率太低。
工程检查项
每次执行 click 前保存：原始截图、发送给模型的截图、display 尺寸、返回坐标、缩放后坐标、点击 overlay。

模型与 Thinking Effort 怎么选

场景推荐原因
多数普通网页自动化Sonnet 4.6 + medium thinking点击精度、推理、成本均衡；中等思考通常性价比最高。
复杂一次性任务 / 专业软件 / 高分辨率Opus 4.7 + high更强推理、更高像素预算；high 接近最高成功率但成本低于 max。
高吞吐、低成本low thinking 或 Haiku短流程、稳定 UI 下足够；少量 thinking 反而减少重试。
复杂规划 + 机械点击Planner/Advisor + Executor强模型负责策略，便宜/精准模型负责执行。

长任务上下文管理：三件套

默认组合

  1. Prompt cache breakpoints
  2. Batch rolling buffer
  3. LLM compaction
Cache

断点别只放稳定前缀

1 个放 system/tools，最多 3 个放最近 tool_result，每轮移动。

Buffer

批量删旧图

保留最近 3 张，超过阈值后每 25 张批量替换为 [Image omitted]，避免 cache 每轮失效。

Compact

摘要替代历史

接近窗口上限时总结用户指令、约束、已做、失败、当前状态、下一步。

安全设计：Browser Use 不是普通 API 调用

网页内容不是用户指令

系统 prompt 必须明确：网页、邮件、图片、文档里的文字都是不可信环境内容，不能覆盖用户目标。

高风险动作必须暂停

提交表单、发消息、付款、删除、改权限、下载/运行文件、外发数据前必须 human-in-the-loop。

最小权限

不需要下载就禁下载；不需要发邮件就不暴露邮箱；不需要本地文件就不给文件系统。

全链路审计

记录每个动作、截图、URL、模型输出、确认记录，方便追责和迭代。

Web / Mobile 云端 Browser 与 PC 本机 Browser 的产品解法

这也解释了为什么用户会觉得“agent 不靠谱”：他们不知道当前端的 browser use 能力发生了降级。

能力云端 BrowserPC 本机 Browser产品提示
登录态 / Cookie通常没有可复用涉及“我的账号/后台/登录”时建议 PC
企业内网可能访问不了跟随用户网络检测内网域名时提前说明
本地文件受限更自然上传/下载/读取文件时建议 PC
插件/证书/系统弹窗缺失或不可见完整遇到系统级 UI 要 fallback
复杂交互视口/状态可能不同更贴近用户所见失败后归因为环境限制，而非模型差
推荐不是简单弹一句“PC 更好”。 应做成：任务风险识别 → 能力差异提示 → 一键切到 PC 继续 → 失败后环境归因。

0-1 Checklist

  • 固定或自适应缩放截图，禁止直接发原生 4K。
  • 声明 display 尺寸等于实际发送图片尺寸。
  • 执行 click 前坐标 scale back。
  • 文本指令放在截图前。
  • 启用 zoom 处理密集 UI。
  • 小目标优先 keyboard / DOM / JS。
  • 每步记录截图、坐标、tool call。
  • 提供 trajectory viewer 和 click overlay。
  • 长任务保留最近 3 张截图。
  • 旧图批量 prune，避免 cache 每轮失效。
  • 接近上下文上限时 compaction。
  • compaction 摘要保留用户原话和失败尝试。
  • 网页内容视为不可信。
  • 高风险动作 human-in-the-loop。
  • 按端能力选择云端/本机 browser。
  • 建立真实任务 eval set，不靠感觉调参。

最终建议：先做“窄而稳”，再做“广而强”

第一周

只支持 3 类低风险任务，跑通截图、坐标、日志、回放。

第一个月

加入上下文压缩、安全确认、失败归因和端能力路由。

规模化

沉淀 workflow demo、teach mode、advisor、评测集和权限治理。
