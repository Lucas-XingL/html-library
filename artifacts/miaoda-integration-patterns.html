Multi-Agent 架构 · 通用 Agent × 妙搭 Coding Agent · 接入方案

主 Agent 怎么接妙搭？
5 种方案 + 流程图 + 优劣对比

结论先行：5 种接入方案分别是 RPC、Sub-agent、Skill、Hand-off、A2A。 给你的推荐路径是「A → B → 局部 D」三段式： 起步用 RPC（最简单），coding 任务复杂后升级 Sub-agent（能跑完整循环）， 需要沉浸式 IDE/Canvas 体验时再做 Hand-off（整个会话交给妙搭）。

主 Agent（你） 妙搭 Agent 工具 / 服务 数据流

1. 用厨房类比理解 5 种方案

把你的主 Agent想象成你家厨房，妙搭是外面的专业餐馆。「让妙搭帮你做菜」可以有 5 种方式：

方案厨房类比含义
A · RPC打电话点外卖下单 → 等送达 → 收菜，你不用操心怎么做的
B · Sub-agent雇个临时工来你家把"做一桌菜"的任务交给他，他自己买菜、备料、出餐，最后把成品给你
C · Skill买他们的菜谱不联系餐馆，把菜谱（prompt + 工具）拿过来你自己做
D · Hand-off把客人介绍过去客人吃这顿就在餐馆里吃，你这边的招待结束
E · A2A 协议两家餐馆有行业对讲机两边的 agent 用统一协议互发消息，谁需要谁喊

2. 上下文：你的架构现状

现状：Doc/PPT/Excel 都是你自己团队搞定的"垂直子 Agent"。妙搭是另一支团队的成熟产品，不是你能直接重写的。所以接入方式要比内部 sub-agent 更"外交"一些。

3. 五种接入方案 · 逐个画

方案 A

RPC · 把妙搭当一个工具调

主 Agent 在自己的 tool 列表里加一个 miaoda_code(task, context)。命中时打 HTTP/gRPC 请求过去，妙搭服务端跑完一次性返回结果。

本质：妙搭对你来说是个"黑盒服务"，你不关心他们里面是 1 个 agent 还是 10 个。一个 request/response 来回。

优势

  • 实现最简单，1–2 天就能联调
  • 边界清晰，他们的 bug 不会污染你的链路
  • 无状态、可并发、好运维
  • 主 Agent 完全保留控制权

劣势

  • 不支持流式 / 实时反馈（除非 SSE，多一层复杂）
  • 长任务（>30s）需要轮询 / webhook，体验差
  • coding 任务往往是"多轮迭代"的，单次调用很受限
  • 主 Agent 看不到中间过程，无法纠偏
方案 B

Sub-agent · 主 Agent 派生一个妙搭子 Agent

主 Agent 用 delegate_task 拉起一个"妙搭子智能体"，把目标 + 上下文交过去。妙搭 agent 有自己的完整 loop：自己的模型、自己的工具集、自己的工作目录。跑完后把摘要 + 产物链接回报主 Agent。

本质：主 Agent "委派一个完整任务"，子 Agent 有完整 agent loop（不是单次调用），跑完一次性回报结果。 像把项目外包给一个有完整生产能力的小作坊。

优势

  • 能处理复杂、多轮、多工具的 coding 任务
  • 主 Agent 上下文不被污染（子 agent 自己消化）
  • 支持并发派生多个子任务
  • 主 Agent 仍是"老板"，可中断 / 取消

劣势

  • 需要约定标准的任务交接协议（目标、上下文、产物格式）
  • 子 Agent 跑得久，主 Agent 要么阻塞要么定期反查
  • 主 Agent 看不到中间过程，纠偏只能在轮次之间
  • 资源（VM / GPU）按需启动，成本高
方案 C

Skill · 只拿菜谱，不联他们服务

不调妙搭服务，把他们的核心资产——prompt 模板 + 工具说明 + few-shot 数据——以 Skill 形式注入你自己的主 Agent。模型还是你的，工具还是你的，只是"行为模式"学他们。

本质："知识转移"而非"服务调用"。妙搭交付一份 Skill 包 给你，运行时和他们已无关系。

优势

  • 运行时零延迟、零服务依赖
  • 不存在网络 / 鉴权 / SLA 风险
  • 主 Agent 完全统一（一个模型一套上下文）
  • 成本最低

劣势

  • 失去他们独家的模型优势（如果他们模型比你强）
  • 失去他们独家的工具生态（IDE、预览、部署等）
  • 资产需要持续同步更新，容易过时
  • 不能利用他们的算力 / 沙箱基础设施
方案 D

Hand-off · 完全交接给妙搭

主 Agent 只做"接待 + 分流"，命中 coding 意图后把整段会话交接给妙搭。之后用户和妙搭直接对话，你这边只在最终需要回流时再接管。

本质：你不再是中间人，会话所有权移交。最纯粹的"客人转介绍"。

优势

  • 用户能用到妙搭完整原生体验（IDE、Canvas、预览）
  • 无需做协议适配，他们的产品力 100% 释放
  • 主 Agent 链路短、轻、好维护
  • 双方团队边界最清晰

劣势

  • "换了个产品"——用户体验断层
  • 主 Agent 看不到 coding 中间产物，跨模态串联难做（例如：写完代码再生成 PPT 介绍）
  • 会话回流难（什么时候算结束？怎么把结果带回？）
  • 商业 / 计费 / 用户归属问题
方案 E

A2A 协议 · 两个独立 Agent 互发消息

采用标准的 Agent-to-Agent 协议（如 Anthropic ACP、Google A2A、MCP-Agent），两边都是独立 Agent，通过消息总线对等通信。主 Agent 既可以"喊妙搭做事"，妙搭也可以"反向请求主 Agent 给上下文"。

本质：两个 Agent 是对等节点，靠协议互发消息，没有谁是谁的工具。未来 multi-agent 生态的方向。

优势

  • 架构最干净，双方完全解耦
  • 支持双向通信、异步、streaming
  • 未来再接其他 Agent 边际成本低
  • 符合行业演进方向（ACP / A2A）

劣势

  • 双方都要按协议改造，启动成本最高
  • 协议本身还在演化，标准不稳
  • 缺乏统一调试 / 观测工具
  • 用户场景不大时是过度设计

5. 决策树 · 该选哪个？

6. 给你的推荐路径

不要一上来就追求"最优雅"的架构，分阶段演进是工业实践通行做法：

阶段 1
2 周内：RPC 联调 — 妙搭暴露一个 POST /v1/code/task，主 Agent 当 tool 调用，验证可达 / 鉴权 / 产物回传
阶段 2
1–2 月：升级 Sub-agent — coding 任务变多轮、变长时，把 RPC 升级为"派生子 Agent"，主 Agent 只负责派单
阶段 3
当用户要原生 IDE：开局部 Hand-off — 检测到"我要进入开发模式"时整段交接，做完再回主 Agent
阶段 4
3+ 月后：评估 A2A — 如果你还要接更多第三方 agent（设计、营销、客服）才上 A2A，否则别折腾
不推荐：纯 Skill（C）路线。原因：妙搭是一支独立产品团队、有自己的模型 / IDE / 沙箱，把他们降级成"prompt 资产"既不尊重他们的能力，也拿不到他们最大的价值。
什么时候考虑 C：你只想要"妙搭做小函数生成"这种轻量场景，且不需要他们的运行时基础设施。

7. 起步方案 (RPC) 的工程细节

必须和妙搭对齐的 5 件事

项建议默认
鉴权双向 mTLS 或 JWT（内部服务首选 JWT）
任务模式同步快任务（< 10s）走 RPC；超时改异步（create_task + webhook）
上下文格式主 Agent 把 user_intent + 历史摘要 + 关键产物 URL 打包成 JSON
产物回传返回 URL 列表（妙搭文档 / 预览 / Git 仓库），主 Agent 上下文里只保留 URL，不内嵌代码
失败 / 重试幂等 task_id；失败按错误码分类（用户错 / 模型错 / 系统错），主 Agent 决定是否重试

Tool 定义示例（给主 Agent 看）

{
  "name": "miaoda_code",
  "description": "调用妙搭 coding agent 完成代码相关任务：写一个网页/小工具/数据看板/小程序",
  "parameters": {
    "task": { "type": "string", "description": "用户原始诉求 + 你的理解" },
    "context": {
      "type": "object",
      "properties": {
        "history_summary": { "type": "string" },
        "referenced_urls":  { "type": "array", "items": { "type": "string" } },
        "preferred_stack":  { "type": "string", "enum": ["html", "react", "python", "auto"] }
      }
    },
    "mode": { "type": "string", "enum": ["sync", "async"], "default": "sync" }
  }
}

8. 新手常踩的 4 个坑

坑 1

把代码内容回主 Agent 上下文
几千行代码灌进主 Agent 会爆 context、拖慢一切。永远只回 URL + 摘要。

坑 2

意图锁定导致路由僵化
"只要听到 code 就路由给妙搭" → 用户问"这段代码有 bug 吗"也被强制提单到妙搭。用模型判断而不是关键词锁定。

坑 3

主 Agent 阻塞等 sub-agent
妙搭跑 30 分钟，你的主 Agent UI 也卡 30 分钟。用任务 ID + 后台轮询 + 通知模式。

坑 4

没约定产物的"权威源"
代码到底在主 Agent 知识库里还是妙搭那边？编辑修改谁是 source of truth？明确"妙搭 own 产物，主 Agent 只 own 引用"。

9. 一页带走的 3 件事

1

先 RPC，不要硬上 A2A。 跑通 > 优雅。

2

Coding 任务复杂后升级 Sub-agent。 主 Agent 做派单，子 Agent 跑完整循环。

3

用户要原生 IDE 体验时再做 Hand-off。 不要把"沉浸式开发"塞回聊天框。
