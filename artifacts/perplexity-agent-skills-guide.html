写 Agent Skill ≠ 写代码
它是给模型构建的 context, 不是给人读的文档

Skill 是路由触发器 + 渐进式知识包 + 不断累积的 gotchas 列表。它的最高准则只有一条:每一个 token 都要赚回它的注意力成本。

1七个先读结论

如果你只有 30 秒,只看下面 7 张卡片。
CONCLUSION 1

Skill 是文件夹,不是文件

SKILL.md 是 hub,scripts / references / assets 是 spoke。复杂性本身是 Skill 的特性,不要硬塞进一个 markdown。

CONCLUSION 2

description 比正文更难写

description 是路由触发器,不是说明文档。以 Load when… 开头,< 50 词,描述用户意图,不要总结工作流。

CONCLUSION 3

每个 Skill 都是一笔税

每个 session、每个用户都在为它的 100 tokens 索引付费。问自己:“没这句指令,agent 会做错吗?”答案是否,就删。

CONCLUSION 4

Context 分三层,门槛递减

Index ≤ 100 tokens · Body ≤ 5,000 tokens · Runtime 无上限。越早期的层,门槛越严。

CONCLUSION 5

Gotchas 是最高价值内容

负面示例 > 正面示例。先薄起步,跌一次坑加一条,自然长出来。维护期主要做"追加",不要不断改 description。

CONCLUSION 6

容易解释的内容 → 删掉

模型已经知道。git 命令串、README、system prompt 复述 — 全都不需要 Skill。Skill 只装"模型不知道的判断"。

CONCLUSION 7

新增 Skill 会无形中伤害所有 Skill (action at a distance)

因为路由是隐式模式匹配,任何 description 的细微改动都会外溢到其他 Skill 上。所以:先写 evals,再写 Skill。改 description 必须配套写 eval。

2为什么"写代码的直觉"在 Skill 上行不通

PEP20 的 20 条箴言里, 至少一半在 Skill 上是错的。下面 5 条对比最直观:
Zen of PythonZen of Skills
Simple is better than complex
简单胜于复杂		 → Skill 是一个文件夹,复杂性就是特性
Explicit is better than implicit
显式优于隐式		 → 激活靠隐式模式匹配;内容按需渐进展开
Sparse is better than dense
稀疏优于密集		 → context 很昂贵, 追求每个 token 最大信号量
Special cases aren't special enough to break the rules
特例不足以打破规则		 → Gotchas 就是特例, 也是价值最高的部分
If easy to explain, may be a good idea
容易解释就是好主意		 → 容易解释 = 模型已经知道, 删掉

3Skill 的目录结构: Hub & Spoke

SKILL.md 是中心枢纽, 其他文件按需被 hub 路由调用。这种"中心+辐射"模式让 Skill 保持紧凑, 又能承载复杂度。

每个 spoke 的职责

  • SKILL.md 唯一必需文件, 含 frontmatter + 正文
  • scripts/ 让 agent 直接跑, 不要每次重新发明
  • references/ 体量大的资料, 只在条件触发时读
  • assets/ 输出模板、JSON schema、固定数据
  • config.json 首次运行时的用户问询
  • 多层级嵌套适合复杂领域 (例如 1,945 条税法条款 → 20 大类 → 子主题)

为什么不用单文件?

  • 把所有内容塞 SKILL.md → 模型很难导航
  • 分层后模型可以"先选大类, 再选子项",分类难度指数下降

4Context 三层预算: 越早期, 门槛越严

从左到右,准入门槛递减; 但从右到左, 影响范围递增。
Tier 1 · 索引层

Index

~ 100 tokens / Skill
  • 加载内容: 每个非隐藏 Skill 的 name + description
  • 注入位置: system prompt 开头
  • 谁付费: 每个会话、每个用户、永远
⚠️ 准入门槛极高 — description 必须极短极密
Tier 2 · 加载层

Load

~ 5,000 tokens / Skill
  • 加载内容: 完整 SKILL.md 正文
  • 触发条件: 模型调用 load_skill() 之后
  • 谁付费: 余下整个对话, 直到 compaction
⚠️ 一个 thread 常并发加载 3-5 个 Skill, 成本叠加
Tier 3 · 运行层

Runtime

∞ unbounded
  • 加载内容: scripts / references / assets / subskills
  • 触发条件: agent 真的读它时
  • 谁付费: 只有具体那次调用
✅ 这里才放无限分支逻辑 — 门槛最低

5何时需要 Skill, 何时不需要

第一原则推不出答案 — 让 agent 先在没有这个 Skill 的情况下跑几组 hero query, 看它做得够不够好。

✓这时候你确实需要 Skill

  • 没有特殊 context, agent 必然做错的任务
  • 多次运行间存在你无法接受的不确定性
  • 知识本身稳定但不在训练集里 (内部知识、知识截止后的新事)
  • 企业专有工作流或者品味/审美 (字体、设计判断)

✗这时候你不需要 Skill

  • 只是一串 git 命令 — 模型本来就会, 这是文档不是 Skill
  • 复述 system prompt 里已经有的内容 — 多数请求都用到的应该放全局
  • 内容变化比你能维护的速度快 (远程 MCP 工具版本频繁变) — 写进去只会 drift
  • 能用 prompt 里一句话解决的事

6"Description" — 全 Skill 最难写的一行

它是路由触发器, 不是内部文档。每一个词都在抢模型的注意力。
BAD
"This Skill monitors pull requests and reports CI status to the user."
→ 在描述 Skill 做什么 (像内部 README)
GOOD
"Load when the user says babysit my PR, watch CI, or make sure this lands."
→ 描述用户什么时候会触发, 用真实查询语料
✓ 以 Load when... 开头 ✓ ≤ 50 词 ✓ 直接引用真实用户原声 ✗ 不要概述 workflow ✗ 不要写"This Skill does..."

7构建流程: 6 步 (从第 0 步开始)

注意: 不是先写正文。先写 evals, 再写 description, 正文才是第 2 步。
STEP 0

写 evals

真实用户查询 + 已知失败案例 + 邻域混淆案例。反例比正例更有力。

STEP 1

写 description

最难的一行。先把路由调对, 再管内容。

STEP 2

写正文

跳过显而易见的命令串。用意图描述,不要写死步骤。重点放 gotchas。

STEP 3

用上层级

条件分支、大体量内容拆到 scripts/ references/ assets/。

STEP 4

分支迭代

在分支上跑大量 eval。description 的字词调整放在这一步, 不要在合入后改。

STEP 5

Ship

提交一个完整变更集 + eval 集。reviewer 会感谢你。

8维护期: Gotchas 飞轮

Skill 上线后, 不要再改 description。维护几乎全是"追加 gotchas"。看到失败 → 加一条。
agent 在某事上失败
→
追加一条 gotcha
agent 跑偏加载了它 (不该加载时加载)
→
收紧 description + 加负例 eval
agent 该加载没加载
→
补关键词 + 加正例 eval
system prompt 发生变化
→
检查冲突或重复

9需要哪几类 Eval

Perplexity 至少跑这三类, 并且要在多个模型 (Sonnet / Opus / GPT) 上各跑一遍。
EVAL 1

加载行为

该路由时路由到吗? 不该路由时被拦住吗? Precision / Recall / Forbidden checks。新 Skill 不能破坏既有边界。

EVAL 2

渐进加载

Skill 加载后, agent 有没有继续读取该读的 reference / asset 文件? 例如 finance Skill 是否读了 FORMATTING.md。

EVAL 3

端到端任务

跑完整 agent loop, 用 LLM judge 按 rubric 打分。验证最终交付质量, 而不只是路由对错。

10带走 3 条

核心 takeaway

  1. Evals 先于 Skill。包含负例和针对邻域 Skill 的 forbidden load 测试。这是唯一能保护"新增 Skill 不伤害老 Skill"的护栏。
  2. description 是最难的部分。"Load when…" 起头, 每个词都在抢注意力 — 反复推敲到不能再短。
  3. Gotchas 价值最高。先薄一点, agent 跌坑就追加。Skill 是 append-mostly, 不要不断改 description。
